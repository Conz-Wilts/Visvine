## Task

Server library for the marketplace lifecycle over the Prisma models from tools-schema. Keep pure decision logic separate and tested; DB code thin.

**lib/tools/requirements.ts** (pure): `computeRequirements(perimeter: ToolPerimeter, available: { connectors: string[]; types: string[]; agents: string[] }): { connectors: string[]; types: string[]; agents: string[] }` = declared items with NO match in the space (globs like `deal-*` count as satisfied when at least one match exists; `*` alone is never a requirement); `isDegraded(req)`. `describeRequirements(req): string[]`.

**lib/tools/registry.ts**: `publishTool(p, context, spaceId, name, { note? }): Promise<{ version: AppToolVersion } | { error }>` — loads the working copy build (must be ok), the three sources, computes next `version` = max(existing for key)+1, snapshots EVERYTHING into `AppToolVersion` with status 'pending', `authorUserId` = the caller, `key` = `${spaceId}/${name}`; also bumps `version:` in the index note frontmatter via `writeGated` (origin 'system' or the caller). Only space admins (`isAdmin`) may publish; refuse if a pending version already exists for the key. `withdrawVersion(versionId, callerId)`. `listReviewQueue()`, `reviewVersion(versionId, decision: 'approved'|'rejected', reviewer: { userId, email }, note)` — super-admin only (`isSuperAdmin(email)`); on approve, mark every install of the same key whose version < this one with `pendingVersionId` = this id (an admin-approved upgrade). `browseVersions({ q?, cursor? })` — latest APPROVED version per key with author display name and install count; `getVersion(id)`; `versionHistory(key)`; `previousApprovedVersion(key, before)` for diffs. `perimeterDiffForVersion(versionId)` uses `diffPerimeter` against the previous approved version (or EMPTY).

**lib/tools/installs.ts**: `listInstalls(spaceId): InstallSummary[]` (`{ id, key, slug, title, description, version, enabled, requirements, degraded, typeClaims, rail: config.surfaces.rail, types: config.surfaces.types, pendingVersion: {id, version, perimeterDiff} | null }`), `installVersion(spaceId, versionId, actor: { userId; email }, opts: { slug?; typeClaims? })` — admin only; version must be approved; slug defaults to the tool name, de-duplicated within the space; compute requirements against the space (connectors = `runnableConnectorNames`/listConnectors names, types = Space.nodeTypes names lower-cased, agents = agent brief names); resolve `typeClaims`: for each `surfaces.types` entry, `page` on a built-in type is downgraded to `tab`; a `page` claim on a custom type already claimed by another install is NOT auto-granted (left out of typeClaims and reported in the result as `conflicts` for the admin to pick); also **auto-add the rail item**: if `config.surfaces.rail` exists, append `tool:<slug>` to `featureConfig.order` via `mergeFeatureConfig` + `updateSpaceConfig` (never a whole-value PUT). `uninstall(spaceId, installId, actor)` removes the row and the rail key from order/more. `setInstallEnabled`, `setTypeClaims(spaceId, installId, claims)` (validates one-page-per-type), `applyUpgrade(spaceId, installId, actor)` (moves to pendingVersionId, recomputes requirements, clears pending), `refreshRequirements(spaceId)` (call after connectors/types/agents change is optional; expose for the UI's 'Re-check'). Export `installedToolsForClient(spaceId): InstalledToolDto[]` = `{ key, slug, title, icon, label, href: '/t/<slug>', enabled, degraded, types: typeClaims }` — the shape the space DTO will carry.

Tests: requirements logic; typeClaims resolution (built-in downgrade, conflict); slug de-dup; version numbering — write these against pure helpers extracted from registry/installs (`nextVersionNumber`, `resolveTypeClaims`, `uniqueSlug`). Acceptance: tsc/lint/test/knip clean.

## Outcome

Built the marketplace lifecycle library over the tools-schema Prisma models: requirements.ts (pure), registry.ts (publish/withdraw/review/browse/history/diff) and installs.ts (install/upgrade/enable/claims/uninstall/refresh + the space-DTO slice), with the four rule-bearing decisions extracted as pure, tested helpers. 36 new node:test assertions pass; full repo is green — `tsc --noEmit` clean, `pnpm lint` clean, `pnpm test` 880/880 pass, `knip` reports nothing in my files (its only remaining entries are task 010's lib/tools/service.ts exports awaiting wave-3 consumers).

**requirements.ts** — `computeRequirements`, `isDegraded`, `describeRequirements`, plus `requirementsEqual` (lets a re-check skip a no-op write) and `parseRequirements` (defensive decode of the JSON column). The satisfied-test asks the perimeter's OWN gates (`refuseConnector`/`refuseType`/`refuseAgent` against a single-entry perimeter) rather than a second copy of the matching rule — a checklist that said "satisfied" while the bridge refused would be worse than none. `*` alone is never a requirement, `deal-*` is satisfied by one match, note globs never produce requirements.

**registry.ts** — `publishTool` refuses non-admins and non-compiling working copies, reuses task 010's `getBuild`/`toBuildSummary`/`readToolSources`/`toolDiagnosticLine` rather than re-reading the build row, snapshots config/perimeter/three sources/both bundles, and picks its version number under a `pg_advisory_xact_lock` on the key so two concurrent publishes can't both pass the one-pending check. `reviewVersion` is super-admin only and, on approve, flags every install pinned to an older version with `pendingVersionId`. `browseVersions` folds latest-approved-per-key with author name + install count (documented in-memory fold: the registry is review-gated and small). Also `withdrawVersion`, `listReviewQueue`, `getVersion`, `versionHistory`, `previousApprovedVersion`, `perimeterDiffForVersion`, and the shared `decodeToolConfig`/`decodeToolPerimeter` decoders installs.ts uses. Pure + tested: `nextVersionNumber` (highest EVER, so a rejected v3 still burns the number), `toolKey`.

**installs.ts** — pure + tested `uniqueSlug` (truncates so the result stays a valid TOOL_NAME_RE slug) and `resolveTypeClaims` (built-in/unknown `page` → `tab` + reported as `downgraded`; a `page` on a custom type another install owns is left OUT of the claims and reported as a `conflict` with the holder's slug). Every write gates on `isAdmin` and runs the row write and the `featureConfig` change inside one `updateSpaceConfig` callback, using its transaction and per-space advisory lock — which is also what makes slug de-dup and one-page-per-type safe against two admins pressing Install at once. `installVersion` never refuses on unmet requirements (installs degraded, per the brief). Plus `uninstall` (idempotent deleteMany + rail key out of order/more/adminOnly), `setInstallEnabled`, `setTypeClaims` (rejects undeclared types, refuses a taken page naming both sides), `applyUpgrade` (recomputes requirements, re-resolves claims, follows the new config's rail, clears a vanished offer), `refreshRequirements`, `listInstalls` and `installedToolsForClient`.

**Deviations worth recording.** (1) `publishTool(p, context, name, opts)` drops the task's redundant `spaceId` argument — it comes from `context.spaceId`, so principal/context/key can't disagree. (2) Results are the codebase's `{ ok: true, … } | { ok: false, status, error }` (lib/agents/service.ts#ActivateResult) rather than `{ version } | { error }`, so wave-3 routes get their status code; publish also returns `warning` for the case where the registry row landed but the note bump didn't. (3) The index-note `version:` bump writes with origin `'edit'`, not `'system'` — `'system'` is not a `NoteRevisionOrigin`, and `'edit'` is the human origin that task 006's `tools/` AI freeze deliberately lets through; it is a targeted line rewrite, not a `joinFrontmatter` round trip, so hand-written YAML keeps its formatting. (4) `setInstallEnabled`/`setTypeClaims`/`refreshRequirements` take `actor` (the task omitted it) because they are admin acts. (5) "Built-in" for page claims is derived from `NodeTypeConfig.scope === 'note'` (member-invented ⇒ pageable) rather than duplicating config.ts's private BUILT_IN_TYPES list — same rule, one source. (6) Available types are the space's stored `nodeTypes` UNION `DEFAULT_NODE_TYPES`, because `findNodeTypeConfig` resolves a built-in whether or not the column lists it, and a Tool declaring `person` must not read as missing. (7) Rail placement: appending to an EMPTY `featureConfig.order` would rank the Tool first, and the first visible entry is the tab members land on — so an absent order is materialised as the registry order first, with the Tool after it. (8) Availability is read through the acting admin's principal via `principalForUser` (admins bypass every context gate, so it is the whole space) rather than inventing a system principal, which nothing in the codebase constructs. (9) I dropped a draft `installedConfig` helper once task 011's `lib/tools/target.ts` landed with its own install lookup, to avoid two doors on the same row.
