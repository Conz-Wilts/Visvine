## Task

The Visvine-side host for a Tool. Nothing here runs inside the iframe.

**app/api/tools/frame-token/route.ts**: POST `{ target: BridgeRequest['target'] }` → `requireSession()` → membership/readability check identical to the bridge's target resolution (import a shared helper if tools-bridge-server has landed `lib/tools/target.ts`; if not yet present at your start, do the check inline with prisma + `isAdmin`/membership and leave a TODO comment naming `resolveBridgeTarget` — the wave-3 audit will unify) → returns `{ token, frameUrl }` using `mintFrameToken` + `frameUrl` from lib/tools/origin.

**features/tools/lib/theme.ts**: `collectThemeTokens(doc: Document): Record<string,string>` — reads computed CSS custom properties from `:root`/body that Tools may use: `--color-brand-green` (the accent from ThemeContext) plus the app's colour/font tokens (grep apps/web/app/globals.css and features/shared/contexts/ThemeContext.tsx for the variable names) and maps them to `--vv-*` names documented in the kit; pure over a `getComputedStyle` result so it's testable with a fake.

**features/tools/lib/hostBridge.ts**: `createHostBridge({ iframe, frameOrigin, target, onError, navigate })` — listens for `message` events, verifies `event.source === iframe.contentWindow` and `event.origin === frameOrigin`, validates with `isFrameMessage`, on `visvine:ready` posts `visvine:init` (theme, subject, install/preview, degraded, viewer), relays `visvine:call` → `POST /api/tools/bridge` (fetchJson, same-origin, credentials) → posts `visvine:result` (errors mapped, never thrown), handles `visvine:resize` (min 320px, max the pane height; report height to React), `visvine:error` (surface the error card), `visvine:navigate` (only relative in-app paths — reject `//`, schemes, and anything outside `/`), pushes `visvine:theme` when the accent changes and `visvine:subject` when the subject prop changes; `dispose()`. Unit-test with fake iframe/window objects.

**ToolFrame.tsx** (client): props `{ target, subject?, title, mode: 'page'|'tab'|'preview', className? }`; mints a token on mount (and re-mints on 403/expiry), renders `<iframe sandbox="allow-scripts" referrerPolicy="no-referrer" allow="" src={frameUrl}>` (NO allow-same-origin, no allow-top-navigation, no allow-popups, no allow-forms), fills the main content area (`w-full`, height = available pane height with internal scrolling inside the frame; the frame may only ever be inside the page body — never portal it), shows a skeleton until `visvine:ready`, a `DegradedBanner` when `degraded` (lists missing requirements, links admins to `/tools?tab=installed`), a `ToolErrorCard` on crash/timeout (message, 'Report' link `mailto:`-free — link to the tool's `/directory/tool:<name>` page or the marketplace entry, and a 'Reload' button); a 15s ready timeout → error card. `ToolErrorCard`/`DegradedBanner` are simple presentational components using existing UI primitives from apps/web/components/ui.

**PerimeterSummary.tsx** (`{ perimeter, diff? }` → grouped chips: reads/writes/types/connectors/agents, added in green/removed in red when a diff is passed) and **CodeDiff.tsx** (`{ before, after, filename }`) over **features/tools/lib/diff.ts** (a small pure LCS line diff → hunks; tested). Acceptance: tsc/lint/test/knip clean.

## Outcome

Landed the Visvine-side host for a Tool: the frame-token route, the postMessage relay, theme collection, the ToolFrame client and the four presentational components, with 41 new tests. tsc reports no errors in any file I touched, `eslint . --max-warnings=0` is clean across the whole app, the full suite is 880 pass / 0 fail, and knip flags nothing of mine.

**hostBridge.ts** — `createHostBridge({ iframe, hostWindow, frameOrigin, target, init, maxHeight, onReady, onResize, onError, navigate, send? })` → `{ setTheme, setSubject, dispose }`. Every message passes three gates before a field is read: `event.source === iframe.contentWindow`, `event.origin === frameOrigin`, `isFrameMessage`. One correction to the task's assumption, and it matters: a frame sandboxed without `allow-same-origin` has an **opaque origin**, so `event.origin` is the literal string `"null"` and never the tools origin — and an opaque origin matches no serialized `targetOrigin`, so `'*'` is the only value that can reach the frame at all. The module exports `SANDBOXED_FRAME_ORIGIN = 'null'` (what ToolFrame passes as `frameOrigin`), keeps the strict equality check, and derives the post target from it — `'*'` for the opaque case, the origin itself otherwise, so a future non-sandboxed frame is still addressed exactly. This is not a new leak: a Tool that can read data can already exfiltrate by navigating its own frame, which the wave-4 escape suite covers. `visvine:ready` posts init once (a re-posted `ready` gets nothing); `visvine:call` relays to `POST /api/tools/bridge` with the host's own target (a `target` field smuggled into the frame's message is ignored) and every failure becomes a `visvine:result` — HTTP status mapped to a `BridgeErrorCode`, unreadable bodies collapsed to `internal`, nothing ever thrown; resize clamped to `[320, maxHeight()]` read live; navigate gated by `isInAppPath`; theme/subject pushed only after the handshake and only on change. `HostInit` is a getter so the theme is read at ready time, not at construction — ThemeContext writes its variables in an effect and a child's effect runs first.

**frame-token/route.ts** — `POST { target }` → `requireSession()` → `resolveContext(session, spaceId)` for membership (install: the install row's space, plus `enabled`; preview: `canReadPath` on `tools/<name>/index.md` under the viewer's own principal) → `mintFrameToken` + `frameUrl`. `lib/tools/target.ts` did not exist at my start, so the check is inline with a TODO naming `resolveBridgeTarget` and flagging that the `tools` feature-key gate belongs there too. The response carries `install`/`degraded`/`viewer` alongside `{ token, frameUrl }` — one authenticated round trip, and `viewer.isAdmin` in particular must never be something the page decided for itself. `FrameTokenResponse` is declared once (in hostBridge.ts, since it is three fifths of the init payload) and imported type-only by the route.

**ToolFrame.tsx** — `<iframe sandbox="allow-scripts" referrerPolicy="no-referrer" allow="">`, rendered inline and never portalled (commented as the invariant it is). Mints on mount, re-mints on Reload; skeleton overlays the iframe rather than replacing it (a swapped-out iframe never loads); 15s ready timeout and any `visvine:error` → `ToolErrorCard`; `DegradedBanner` when the install reports missing requirements. Pane height is measured from the frame slot's top to the viewport bottom — the slot's own height never feeds that, so it cannot chase its own tail. `mode: 'page'` fills the pane; `'tab'`/`'preview'` grow to the reported height, floored at 320 and capped at the pane.

**diff.ts** — LCS line diff → unified hunks. Common head and tail are trimmed before the table is built (a one-line edit in a 6000-line file becomes a 1×1 comparison); past 4M cells it degrades to a wholesale replacement and sets `truncated` so `CodeDiff` says so rather than implying an exact comparison. CRLF/LF and trailing-newline differences are not changes; an empty file is zero lines, not one blank one.

**theme.ts** — `collectThemeTokens(doc)` over a pure `themeTokensFrom(read)`. Twelve tokens (accent trio, three surfaces, two borders, three text, body font) published under both the app's own name and the `--vv-*` alias the kit's stylesheet paints from; unset or whitespace-only values take the KIT_CSS literal rather than shipping empty. The marketing face (`--font-brand`) is deliberately not published.

Tests: `tests/tools-diff.test.ts` (14) covers line numbering, hunk framing and merging, `context: 0`, moves, the trim, and the truncation ceiling; `tests/tools-host-bridge.test.ts` (27) covers the handshake and its once-only rule, foreign-origin and foreign-window rejection, eleven malformed messages, target smuggling, all nine status mappings, network and unreadable-body failures, post-dispose silence, resize clamping against a live ceiling, in-app navigation (six refusals including `//host`, a scheme, and a backslash pair), theme/subject push semantics, and the theme collector.
