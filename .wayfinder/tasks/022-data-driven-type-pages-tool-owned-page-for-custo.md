## Task

Surface (b): the profiles/spaces/events analogy for member-invented types.

**lib/tools/typePages.ts** (pure, tested): `BUILT_IN_TYPES` (person, space, event, resource, section, channel, connector, agent, tool, index + synonyms via `entityKindOf`), `resolveTypePage(installedTools: InstalledToolDto[], typeName: string): { owner: { slug; title; key } ; mode: 'page' } | { owner; mode: 'tab' } | null` — built-ins can only yield `tab`; custom types yield `page` for the ONE install whose `typeClaims[type] === 'page'` (ties impossible by construction; if data is inconsistent pick the earliest install and log), `typePagesFor(installedTools): Record<string, …>`, `noteTypeOf(frontmatter): string|null` (lower-cased `type:`).

**features/tools/hooks/useTypePages.ts**: memoised map from `useSpace().currentSpace.installedTools`.

**Note route** (directory/note/[...path]/page.tsx): after resolving the note (you need its frontmatter type — the shell's note surface loads content; find the cheapest existing hook to read the note's frontmatter, e.g. the same fetch NoteContextPanel/`useNote`-style hook uses, or add a light `GET /api/notes/item` read; do not add a new route unless unavoidable), if `resolveTypePage(...)` returns `page` for a non-entity note: tabs become `[{ id:'tool', label: <Type name> }, Context, Raw]`, default active `tool`; when active the page renders `<TypePageTab>` as the page BODY (a `ToolFrame` with `subject = { kind:'note', path, type, title }` and `mode='page'`) while registering `surface: { kind: 'tree-only', notePath }` so the docked tree stays and no note editor is drawn underneath; Context/Raw switch back to the normal note surface. Nothing changes for notes of unclaimed types.

**NodeRoute** ([nodeId]/page.tsx): for built-in entity pages that use `NodePage`/`useEntityChrome` (person, space record, org, resource, connector, agent, tool), when a Tool holds a `tab` claim for that node's type, append a tab `{ id: 'tool:<slug>', label: <tool title> }` after the first tab and before Context/Raw; selecting it renders `<TypePageTab>` with `subject = { kind:'node', nodeId, type, notePath }`. Keep this minimal and generic (one helper that appends tool tabs to a tabs array + one render branch), avoid touching Person/Event redirect logic beyond adding the tab where the tab bar already exists. Person profile uses `PERSON_TABS` — extend the same way.

**TypesPanel.tsx**: show, per custom type, which installed Tool pages it (or '—'), and when more than one install claims `page` for the same type, a picker that PATCHes `typeClaims` on the chosen install (and clears the others) via `/api/communities/[spaceId]/tools/[installId]`. Acceptance: tsc/lint/test/knip clean; manual check with a scaffold Tool claiming a custom type `deal` and a note `deals/acme.md` with `type: deal` (report).

## Outcome

Type-page dispatch is data-driven: a Tool that claims a member-invented type now IS that type's page (first tab on the note route, default active, frame fills the pane, docked tree stays, no editor underneath), a Tool that claims a built-in gets an extra tab after the first tab and before Context/Raw on every entity page that has a tab bar, and the console's Types panel names the Tool that pages each custom type — with a picker when two claim it. tsc, `eslint . --max-warnings=0`, `pnpm test` (964/964, 19 new) and knip are all clean, and the whole thing was driven end to end in a browser against the dev server with a scratch Tool claiming `deal` and a note `deals/acme.md`, then removed again.

**lib/tools/typePages.ts** (pure, 19 tests). `BUILT_IN_TYPES` + `isBuiltInType` compose three existing sources rather than copying any: the ten `DEFAULT_NODE_TYPES`, `entityKindOf`'s synonym table (so `community`/`people`/`organization` can't sneak a page past under an old spelling) and `isReservedTypeName` (which is why `note` and `file` are in the list too — a page claim on `note` would take over every plain note in the space). `resolveTypePage` re-checks the built-ins-win rule on READ, not just on write: a claim row written before the rule existed, or by a future bug, still cannot replace a profile. Two page claims on one type is impossible by construction, so it takes the first and `console.warn`s rather than letting a page flicker between two Tools by render order. Plus `typePagesFor` (the map), `noteTypeOf`, and two exports beyond the brief that the consumers actually need: `typeTabsFor` (plural — NodeRoute's tab ids are `tool:<slug>` precisely so several can coexist, and the page owner is excluded so a Tool never appears as a tab beside itself) and `pageClaimantsFor` (the console's picker needs the full list; `resolveTypePage` is built on it, so there is one rule).

**Deviation worth recording:** `TypePageOwner` carries `id` as well as `{slug,title,key}` — `BridgeTarget {kind:'install'}` names the install id, and the DTO carries it (task 017) exactly so a surface can mount a frame with no lookup of its own.

**The note's own type costs nothing to learn.** No new route: the frontmatter type and title come off the note index (`contextKeys.list`) that the docked tree and the note panel already fetch for every note view, through the same `swrFetch` key — warm or cold, zero extra requests. It is only read at all when the space has a Tool holding a page claim; a space with none takes the identical code path it always did. During that one unresolved window the route registers `tree-only` chrome (the entity routes' own loading state) rather than mounting Tiptap for a note that is about to become a Tool's page.

**NodeRoute stayed minimal and generic:** three helpers (`toolTabId`/`isToolTab`, `withToolTabs`, `useToolTabs`) plus one `ToolTabBody` and one render branch per shell. The tab insertion lives in `useEntityChrome`, so NodePage (org/space record/connector/agent/tool), ResourceNodePage and ContextOnlyPage get it at once; Person got the same through `PERSON_TABS`. Event/Space redirect logic is untouched, per the brief. Tool tabs are LOCAL state with no `?tab=` value — a link can never put a Tool on a built-in page, and a reload lands back on the built-in first tab. A Tool tab whose install has gone falls back to the first tab by the same rule the file already used for retired `?tab=` values (derived, not an effect, on the person page).

**TypesPanel** shows the owner in the same right-hand column tool types use (`—` when nobody pages it), only on `scope: 'note'` types — `pageClaimantsFor` answers empty for built-ins, so no row promises a '—' that could never become a name. The picker PATCHes release-before-claim (losers to `tab`, then the winner to `page`): `setTypeClaims` refuses a `page` on a type another install still holds, so a claim sent first would 409 and leave the disagreement exactly as it was.

**Live check** (dev server on :3000, `community:blackbird-ventures`, admin@local.dev). Created the custom type `Deal` through the real member endpoint, authored/published/approved/installed a scratch Tool claiming `deal` as a page, and wrote `deals/acme.md` (`type: Deal`). Result: tab bar reads **Deal | Context | Raw** with Deal active by default, the frame fills the pane (1091px of a 1221px viewport), the tree stays docked with Acme Corp highlighted, `document.querySelectorAll('.ProseMirror, textarea').length === 0` (no editor underneath), and the Tool reads `subject = {kind: note, path: deals/acme.md, type: deal, title: Acme Corp}`. Context switches back to the real editor with the note's body, Raw shows the raw markdown, and both drop the frame. A sibling note (`deals/pipeline.md`, unclaimed type) is exactly as before: Context/Raw, editor, no frame. A second Tool claiming `person` gave `Profile | Person extras | Context | Raw` — profile still default, the tab renders the frame at content height (335px) with `subject = {kind: node, nodeId: person:amber-joseph, type: person, notePath: people/amber-joseph.md}`, and Profile returns cleanly. Types panel showed `Deal → Deal page`; forcing the impossible two-page-claim state in the DB turned that into the picker ("2 tools claim this page — pick the one that draws it"), and choosing the second left `deal-page-022 → tab`, `deal-page-022b → page` in the row, the panel back to plain text, and the note route rendering **Deal page B**. Everything was then removed — installs uninstalled, notes deleted and purged, version/build/node rows dropped, the `Deal` type taken back out — and re-read as found (blackbird-ventures: 8 built-in types, no installs, trash back to its original 4; the seeded `me:user_dev_admin` `deal-board` install untouched).

**Three things worth knowing for later waves.** (1) `parseToolConfig` refuses `mode: page` on a built-in at COMPILE time, before publish ("A tool may not claim `mode: page` for the built-in type \"person\"…"), so `installs.ts`'s downgrade is a second net and a fixture cannot ship such a claim. (2) `data.js` must assign `handlers.<name> = …`; an ESM `export` fails the build with a clear message. (3) A sandboxed Tool frame's TEXT does not appear in Playwright PNG captures even though the DOM, the accessibility tree, computed styles and `elementFromPoint` all confirm it renders — assert against the frame's DOM, not a screenshot, in tasks 023/024. Separately, and unrelated to Tools: every page logs a CSP error blocking `fonts.googleapis.com` (`style-src 'self' 'unsafe-inline'`), so the brand font "Open Sauce One" never loads and everything falls back to system fonts — pre-existing, app-wide, and outside this task's scope, but somebody should own it.
